## 二 为什么没有照搬「src/engine + src/data + src/pipeline」的结构

审阅给的结构方向是对的，但**直接按它拆会当天断链**。依赖图是 grep 出来的：

```text
bt_r_clause.js  ← phase5_run.js / phase5_sensitivity.js / phase6_stress_v16.js
                ← metrics_v16.js / execution_simulator.js / test_regression.js
bt_engine.js    ← bt_data.js / bt_extended.js / probe_valuation.js
phase2_indices.js ← 上述全部 + phase3_quant_probe.js
```

`require('./bt_r_clause.js')` 是相对**模块所在目录**解析的。把这些文件分别放进 `src/engine/` 与 `src/pipeline/`，第二天早上会有 12 个 `MODULE_NOT_FOUND`，而且它们全都发生在「跑回测」之前，等于整个仓库一次性失去可复现性。

所以阶段一的策略是：**移动，但不拆代码目录**。`src/` 保持一级扁平，只把文档、数据、报告、日志、测试分出去。拆 `src/` 内部结构放在批次 B，且以「改完必须逐字节复现」为前提。

另一个更隐蔽的坑，这次一起解决了：**输出路径**。原来所有脚本写 `fs.writeFileSync(P('x.json'))`，`P = path.join(__dirname, f)`。数据一搬进 `data/processed/`，`phase5_run.js` 会在 `src/` 下重新长出一份 `phase5_backtest_data.json`，而 `metrics_v16.js` 读的是另一份——两份 JSON、谁是真的、没有任何报错。

## 三 迁移机制：三处必须改、一处不能改

| 类型 | 原写法 | 问题 | 迁移后 |
| :--- | :--- | :--- | :--- |
| 目录基准 | `P = f => path.join(__dirname, f)` | 读写都以脚本所在目录为基准，搬家即漂移 | `lib/paths.js` 的 `LAYOUT` 登记表：脚本只说文件名 |
| JSON 引入 | `require('./phase5_backtest_data.json')` | JSON 的 require 绑定模块目录，搬家即 `MODULE_NOT_FOUND` | `JSON.parse(fs.readFileSync(PT.resolve('…'), 'utf8'))` |
| 隐式 cwd | `fs.readFileSync('hs300_daily_2010_2026.json')` | 基准是「运行时 cwd」，从别的目录执行就 ENOENT | `PT.resolve(...)`；加载器内部的 `f` 也改为 `PT.resolve(f)` |
| **计算逻辑** | — | — | **一行不动。** 迁移不是重构的时机 |

`LAYOUT` 是这次的关键设计：**搬迁只改一张表，二十个脚本一行不改**。现在表已按本文件填好，将来再调整目录（批次 B）仍然只改表 + 改 require。
